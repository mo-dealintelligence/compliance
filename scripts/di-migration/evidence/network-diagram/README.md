## The WAF and the NAT

Both are **self-managed rather than the AWS managed service**, by choice — no paid
`serverless.yml` resources. They are drawn and named as what they do, with "self-managed"
on the node:

- **NAT** — a t3.micro EC2 instance (`52.70.24.151`), not a NAT Gateway. IMDSv2, SSM, no key
  pair, ingress only from `10.0.1.0/24` and `10.0.2.0/24`. The only route out of the private
  subnets.
- **WAF** — the firewall's job runs in the application, not in AWS WAF: origin verification
  (`X-Origin-Verify` checked by `OriginVerifyMiddleware`, so a direct hit on a Lambda function
  URL returns 403), rate limiting shared across Lambdas through DocumentDB (`rate_limits`, TTL,
  keyed by credential then IP, fail-open), security headers and log redaction. CloudFront in
  front of it supplies TLS 1.2+ and AWS Shield Standard.

In policy and report text, describe it as a **self-managed WAF** and never as "AWS WAF" — the
managed service is not in the account and an auditor will check.

  from the token, 112 routes authenticated, `/v1/webhook-hubspot` and the duplicate `app.py`
  removed.
- **Fargate egress corrected**: tasks run in the public subnet with their own public IP, so job
  egress does not pass through the NAT (finding A). The previous diagram implied it did.
- CloudFront shown serving both `api.` and `mcp.`; function-URL authorizers shown per function;
  bastion shown as a task definition with no instance running.
- Security Hub and AWS Config dropped: Config is not in use and Security Hub is being retired
  in favour of the monthly configuration-check Lambda (decision D12).

## Open question for the customer version

The customer version deliberately omits data vendors and other third parties. Before it goes to
a customer, confirm that no customer-uploaded data reaches those vendors — if any does, the
diagram needs a line saying so.
